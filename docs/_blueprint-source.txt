Sebelum menghitung skor akhir, setiap metrik diubah menjadi subskor  pada rentang 0–100. 
Untuk metrik yang mempunyai rentang sasaran, gunakan fungsi yang memberikan nilai 
tertinggi di sekitar rentang tersebut dan menurun secara bertahap di luar rentang. Jangan 
menetapkan rentang biologis hanya berdasarkan tebakan.
Formula final:
\[ S=\operatorname{round}\left( \frac{\sum_{i=1}^{6}w_iq_i}{100} \right) \]
dengan  merupakan bobot dalam persentase dan  merupakan subskor yang sudah 
dinormalisasi.
Pseudocode:
function calculateSkinScore(
  subscores: Record<MetricName, number>
): number {
  const weights = {
    hydration: 22,
    oiliness: 18,
    texture: 15,
    pores: 15,
    acne: 18,
    redness: 12,
  };
  // Validate every subscore before this calculation.
  const weightedTotal =
    subscores.hydration * weights.hydration +
    subscores.oiliness * weights.oiliness +
    subscores.texture * weights.texture +
    subscores.pores * weights.pores +
    subscores.acne * weights.acne +
    subscores.redness * weights.redness;

===== PAGE 13 =====
  return Math.round(weightedTotal / 100);
}
Kode di atas baru menghitung skor dari subskor yang sudah dikalibrasi. Fungsi konversi 
metrik mentah menjadi subskor harus dibuat dan diuji secara terpisah sebelum dipakai.

6.4 Ketidakpastian dan kegagalan analisis
Sistem harus mendukung kondisi berikut:
●
Gambar blur, terlalu gelap, wajah tidak terdeteksi, atau gambar tidak sesuai.
●
Provider AI timeout, menolak request, atau menghasilkan data tidak valid.
●
Metrik hilang atau berada di luar rentang.
●
Hasil model terlalu tidak pasti untuk diberikan sebagai estimasi yang berguna.
Dalam kondisi tersebut, backend mengembalikan status gagal atau perlu scan ulang. 
Jangan mengisi metrik yang hilang dengan angka 50 dan menganggap hasilnya valid.
Setiap scan valid menyimpan versi algoritma, model/provider, timestamp, dan status 
kualitas. Perbandingan antar-scan perlu mempertimbangkan perubahan model dan kualitas 
gambar.

7.3 Matching kebutuhan kulit
Aturan awal dari spesifikasi:
●
Estimasi minyak di atas 60 dan indikator pori di atas 60: pertimbangkan produk yang 
sesuai kebutuhan tersebut, dengan bahan seperti niacinamide atau salicylic acid jika 
relevan dengan kategori dan formulasi.
●
Estimasi kelembapan di bawah 55: pertimbangkan produk dengan humektan dan 
bahan pendukung skin barrier, misalnya glycerin, hyaluronic acid, atau ceramide.
●
Kecocokan bahan tidak berarti produk pasti efektif. Formulasi, konsentrasi, jenis 
produk, dan toleransi pengguna juga penting.
Angka 60 dan 55 adalah aturan awal aplikasi yang perlu dievaluasi, bukan batas klinis.
7.4 Formula kecocokan produk
Gunakan skor dasar , penalti , dan hasil akhir :

\[ M=\operatorname{clamp}(B-P,0,100) \]
Jika kebijakan awal menggunakan penalti 8 poin per iritan yang cocok:
dengan  jumlah kecocokan iritan yang unik. Penalti hanya diterapkan satu kali per bahan 
unik, agar sinonim bahan tidak menghasilkan pengurangan ganda.
Hard exclusion harus dilakukan sebelum formula ini. Alergi yang diketahui tidak boleh 
sekadar diberi penalti skor.

Kategorisasi ini hanya memberikan informasi nutrisi umum. Hubungan antara makanan dan

8.3 Algoritma filter alergi
1.
Normalisasi tag alergi pengguna dan pemicu alergi pada katalog.
2.
Cocokkan berdasarkan ID atau kamus sinonim yang dikendalikan, bukan pencarian 
substring bebas saja.
3.
Catat semua kecocokan.
4.
Tandai item sebagai hasAllergyWarning: true jika ada kecocokan.
5.
Untuk alergi yang sudah diketahui, jangan menyajikan item tersebut sebagai 
rekomendasi aman.
6.
Jika data alergen tidak lengkap, tampilkan status yang tidak pasti; jangan 
menyatakan makanan pasti bebas alergen.
Contoh response:
{
  "foodId": "food_001",
  "hasAllergyWarning": true,
  "matchedAllergens": ["seafood"],

18. Master prompt untuk AI coding agent

FACEWISH — MASTER ENGINEERING 
INSTRUCTION
Role
Act as the senior software architect, backend engineer, frontend engineer, and QA engineer 
responsible for delivering FaceWish.
The supplied Complete Technical Blueprint is the project specification. The existing 
repository is the source of truth for what has already been implemented.
Primary Objective
Build FaceWish as a maintainable, secure, testable web application using a hybrid AI + 
deterministic rule-based architecture.
Mandatory Workflow
Phase 0 — Audit
●
Inspect the repository before changing files.
●
Identify the actual frontend, backend, database, dependencies, routes, and tests.
●
Identify what exists, what is missing, and what conflicts with the blueprint.
●
Do not rewrite valid code merely to match a preferred folder structure.
●
Produce an audit report and a prioritized implementation plan.
Phase 1 — Resolve Specification Gaps
Before implementing ambiguous behavior, document and resolve:
●
Metric normalization and the final skin scoring formula.
●
Score labels and boundary conditions.
●
AI provider, output schema, image-quality policy, and failure behavior.
●
Allergy exclusion, sensitivity rules, ingredient synonyms, and unknown ingredient 
handling.

●
API contracts, database relationships, data retention, and authentication.
●
Acceptance criteria for every critical module.
Do not silently invent clinical thresholds or represent unvalidated heuristics as 
dermatological facts.
Phase 2 — Build the Core Engine
Implement independent, deterministic modules for:
●
calculateSkinScore
●
evaluateProductCompatibility
●
filterFoodsByCategoryAndPreferences
●
analyzeIngredientsDeterministic
Add unit tests for boundary cases, malformed inputs, unknown ingredients, duplicate 
ingredient synonyms, and allergy exclusions.
Phase 3 — Build Infrastructure
Implement database migrations, authentication, authorization, profile management, 
preferences, and scan history. Ensure every private resource is scoped to the authenticated 
user.
Phase 4 — Integrate AI
Implement a provider adapter for vision and language models. Validate provider output, 
apply timeouts and bounded retries, and handle failures without producing fabricated results.
Keep AI inference separate from scoring and safety enforcement.
Phase 5 — Integrate the Application
Connect the frontend to the implemented API contracts. Implement loading, empty, error, 
retry, and success states. Avoid mock data in production execution paths.
Phase 6 — Verify
Run lint, typecheck, unit tests, integration tests, and applicable end-to-end tests. Review 
authentication, privacy, file upload handling, API costs, dependency security, and data 
deletion.
Phase 7 — Release Readiness
Prepare staging deployment, environment configuration, database backup and recovery, 
monitoring, migration procedures, and rollback instructions.
Never deploy to production or perform destructive data changes without explicit 
authorization.

Engineering Rules
●
Follow the existing compatible stack unless a justified migration is approved.
●
Keep business logic in testable modules, not UI components or route handlers.
●
Validate every external input and AI response.
●
Keep secrets server-side.
●
Use parameterized queries or safe ORM operations.
●
Document assumptions and unresolved decisions.
●
Do not mark a feature complete unless its acceptance criteria and tests pass.
●
Never claim tests passed without actually running them.
●
Report unavailable dependencies, provider limitations, and remaining risks honestly.

Changes made.

Files created or modified.

Tests executed and actual results.

Security and data integrity considerations.

The next recommended step.
